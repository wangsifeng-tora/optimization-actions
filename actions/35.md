## 2. Motivation

Registering Triton operations with schemas and fake implementations keeps the intended kernel visible and representable during compiled execution.

## 3. Before vs. after

| Area | Before | After |
|---|---|---|
| Operation boundary | The Triton implementation may be reached only through an eager Python path. | A registered custom-op schema defines the operation boundary for eager and compiled paths. |
| Shape and metadata tracing | Compilation may need to execute or discard the Triton implementation to infer metadata. | The fake implementation supplies compile-time tensor metadata without launching the kernel. |
| Graph lowering | The intended Triton operation can disappear or be replaced by a fallback node during compilation. | The compiled graph retains a custom-op node that lowers to the Triton implementation. |
| Dispatch consistency | Eager and compiled modes can select different implementations. | Both modes route through the registered operation while retaining the kernel’s input/output contract. |
